# Lift Board: Progress tab, Spec (progress2)

Owner: Coach (logic). For: Chief of Staff, Builder. Date: Oct 24, 2026. Supersedes the round-1 progress spec (backup `progress-spec.pre-progress2.md`).
Machine-readable rules: `data/progress-rules.json` (generated from `tools/progress_rules.py`). Reference: `data/progress-reference.json`. Shared sample: `data/sample-log.json`.
Generator: `tools/build_progress.py` (deterministic; rerun gives identical files). Tests: `tools/test_progress.py`.

**Label (shown on the tab, exact):** "Strength and performance, not measured muscle growth"

Trends, stalls and wins come from what was logged (loads, reps, hold times, RIR). They describe strength and performance, are modelled, and are not a measurement of muscle growth. No medical or injury advice.

Tags: [E] evidence-based (citation below), [C] convention, [M] modelling choice (ours, tunable). Every threshold in this spec is [M] unless tagged otherwise.

## 0. Focus
- The tab is about **progress (motivation) first, then stalls to adjust**. Order on screen: Wins, Muscles (trend + main lift + latest gain), Needs attention (each with exactly one fix), Lifts (weekly best chart), Effort (RIR).
- **Planned vs done is a footnote only**: one grey line at the bottom, "Planned vs done, last 4 weeks: {done} of {planned} sets" over the last 28 days. No adherence percentages, bars or colours elsewhere on the tab.

## 1. Fixed decisions (Chief of Staff, Oct 24, 2026)
1. **RIR is stored per set as an integer 0 to 4**, where 4 means 4+. It is `null` when skipped. **Only RIR is stored.**
2. **The RPE toggle is display and input only.** RPE = 10 − RIR. RPE chips: **10, 9, 8, 7, ≤6**; ≤6 stores RIR 4. **No half points.**
3. **Legacy values clamp on read:** rir 5 (old "5+") becomes 4; fractional values round to the nearest integer (half up: 1.5 → 2, 2.4 → 2); negatives → 0; non-numeric → null. The stored file is not rewritten; clamping happens in `normalize()` on read.
4. **e1RM uses Epley, load × (1 + reps/30), on done working sets with ≤ 12 reps.** The cap was raised from the old 10 by Chief of Staff; since progress3 `rules.json logger.e1rm_max_reps` is 12, so PR badges (`prs.py`), Train, Log and Progress agree. Always labelled "estimated 1RM". [C] (formula convention; no peer-reviewed source cited)
- RIR chips (RIR mode): 0, 1, 2, 3, 4+. RPE chips (RPE mode): 10 → RIR 0, 9 → RIR 1, 8 → RIR 2, 7 → RIR 3, ≤6 → RIR 4.
- `history.settings.effort` = `"rir"` (default) or `"rpe"`; switching never changes stored data. The RIR-based RPE scale itself comes from Zourdos et al. 2016 [E].

## 2. Units and lift kinds
- Loads are stored in each session's unit (lb default) and converted for display only; internal math is kg via `prs.flatten` (effective load: bodyweight share included for e1RM; *added* load used for "same weight" and plate milestones).
- Each lift gets one kind, derived from `exercises.json` / whiteboard fields (first match, order hold, distance, bodyweight, core, e1rm). No exercise ids are hardcoded except the milestone lifts.

| kind | when | trend metric |
|---|---|---|
| hold | swap.flags has static_hold, or the whiteboard rep range unit is seconds | longest hold, seconds (`set.reps` holds seconds) |
| distance | whiteboard rep range unit is meters (carries) | load-reps index with meters in place of reps (set.reps holds meters) |
| bodyweight | exercises.json bodyweight_fraction > 0 (bodyweight, rings, suspension, assisted machines) | most reps in one working set; added load (or assistance) compared separately |
| core | primary muscle (highest rating) is abs or obliques | load-reps index (no load ever logged -> metric reps) |
| e1rm | everything else | best estimated 1RM per session (Epley, ≤ 12 reps) |

- **No estimated 1RM for bodyweight, ab/core, timed or static-hold lifts.** They use reps, load or hold time.
- High-rep fallback: if any of the lift's non-deload sessions in the 3-month dashboard window (all its sessions if none there) has no done working set of <= 12 reps (e.g. calf raises at 12-20, curls at 10-15), its metric is load_index instead, for the lift card and the dashboard alike, so a lift never mixes estimated 1RM points and gaps.
- `load_index` = best load x (1 + reps / 30) over all working sets, any rep count: the Epley shape used as a trend index for high-rep, core and carry lifts; never shown or named as a 1RM.
- bodyweight lifts trend, stall and dropping on reps only across sessions at the latest session's added load (within half a step; bodyweight-only sessions have added load 0); a heavier added load is a gain, not a drop in reps.

## 3. Per-lift progress
- **Comparable session:** the previous completed, non-deload session that logged the same exercise id (aliases resolved) within the last 56 days.
- **Top set:** heaviest logged (added) load among done working sets; hold lifts: longest hold. **Same load:** within half the smallest real load step (prs.step_kg, gym profile aware).
- **Gain:** load up by more than half a step; or same load and more reps in the best set at that load; or same best-set reps and the same number of sets at that load with more total reps; hold lifts: longer hold.
- **Plain text vs last time:** "+5 lb", "+1 rep at same weight", "−1 rep at same weight", "+5 s", "Same as last time", "First time logged", "No comparable session in the last 56 days". Detail line: "Top set 225 lb × 8 (was 220 lb × 9)".
- **Weekly best:** best metric of the week (estimated 1RM for e1rm lifts); deload sessions excluded; weeks are Monday to Sunday, local date. **PR week:** the week best is above every earlier week best by more than review.flat_pct (1%) (reps / hold: strictly more); the first logged week is the baseline, never a PR week. Deload sessions are left out (§14); a week with only deload sessions has no weekly best.
- **Weekly gain rate:** least-squares slope of the weekly best metric vs week index over weeks with data in the window, as % of the mean per week, window 42 days. Up if > +0.5%/week, down if < -1.0%/week, else flat (same as logger.progress_signals (up > +0.5 %/week, dropping < -1.0 %/week)). Words: "Up about 1.5% a week (about +4 lb estimated 1RM a week)", "Holding steady", "Down about 2% a week". Percent shown to the nearest 0.5 from 1% up, one decimal below 1%.

## 4. Lift status: stalled and dropping
- Status order (first that applies): dropping, stalled, up, flat, down, insufficient.
- **Stalled:** the last >= 3 exposures (non-deload) brought no rep/load gain over the best exposure before them (gain rule above); needs >= 4 exposures and >= 21 days of data.
- **Decline:** an exposure that is not a gain over the reference exposure and whose metric is more than review.flat_pct (1%) below it. **Dropping:** the last 2 exposures are both declines vs the recent best (the best of the 3 exposures before them): 2 sessions in a row below it, as logging-spec §9 performance drop; catches step-wise drops (down, same, down); needs >= 4 exposures.
- Double progression is not a stall: a load jump with fewer reps is a gain (load up), and the stall test compares with the best exposure so far.

## 5. Per-muscle trend
- **Credit:** exercises with an exercises.json rating >= 0.25 for the muscle. **Weight:** stimulus share = credited hard sets in the window (rating x hard sets), same counting as targets.json.
- **Trend:** weighted mean of the %/week of its lifts that have a trend; same thresholds as lifts (window 42 days, thresholds as §3). Minimum: at least one lift with a trend and >= 3 distinct weeks with a credited set in the window.
- **Main lift:** see main_lift_choice (progress7). Before progress7: pinned (history.settings.mainLiftPins[muscle] or report(main_lift_overrides)[muscle], see overrides) else the lift with the most sessions in the window among lifts rated >= 0.5 (none: >= 0.25); ties: higher rating, more credited sets, primary < accessory < isolation, id. Pins live in `history.settings.mainLiftPins` (`{muscle: exerciseId}`).
- **Latest gain:** the main lift's change vs its last comparable session.
- **Stuck (muscle-level stall flag):** muscle trend is flat or down AND its main lift is stalled or dropping AND lifts that are stalled or dropping carry >= 50% of the muscle's weight. One stalled accessory on a muscle that is still going up does **not** flag the muscle.

## 6. Needs attention: exactly one fix each
- Items: deload, muscle_stall, lift_dropping. Order: deload first, then muscle stalls (main lift stall length desc, muscle order), then dropping lifts not already shown as a stalled muscle's main lift (latest drop first). Stuck muscles that share a main lift make one item (muscles listed together, one fix). When the deload is suggested it is the only item: it lists the stuck muscles and dropping lifts it covers (their one fix would be the deload anyway).
- **Fix priority (first rule that applies wins):** deload > sets_up > sets_down > swap > rep_range.
  - **deload**: the deload is suggested (see deload.one_rule): it then becomes the only needs-attention item and covers every stall and drop. Apply edits the board: **false**.
  - **sets_up**: mean credited hard sets of the muscle over the last 2 completed weeks < targets.json min x levelMinFactor (rounded to 0.5): +1 set on the lift (first routine day that has it). Apply edits the board: **true**.
  - **sets_down**: that mean > targets.json max: -1 set on the lift (never below 2). Apply edits the board: **true**.
  - **swap**: the stall has lasted >= 6 exposures: swap the lift for the first swap.py candidate in the same equipment family that fits its template slot and is not already in the routine (none: next rule). Apply edits the board: **true**.
  - **rep_range**: otherwise: move to the other half of the lift's rep range for a while (top-set reps at or below the middle -> upper half, else lower half). Apply edits the board: **false**.
- can_apply = Apply edits the board (analysis ops sets / swap, with Undo). Deload is a week overlay; rep-range advice is display only until the board has a rep-range op.
- Each item carries `fix.apply_edits_board` (boolean) and, when true, `fix.ops` in the board's analysis op format (`sets` / `swap`), applied with the existing preview / Apply / Undo; every op set is checked with the board's preset check before it is offered (no new non-info warnings).
- Far-from-failure note: when the muscle's average RIR (§7) is ≥ 3, the item adds: "Sets ended about 3 reps from failure on average. Sets this far from failure may explain part of the stall." (proximity to failure and hypertrophy: Robinson et al. 2024, Refalo et al. 2023 [E]; the ≥ 3 line is [M]).

## 7. Effort (RIR) summary
- average RIR per muscle over the last 28 days, stimulus-weighted: sum(rating x rir) / sum(rating) over done working sets with RIR logged, rating = exercises.json muscle ratio >= 0.25; 4+ counts as 4; deload sessions excluded. Fewer than 6 such sets -> not shown ("not enough RIR logged").
- Shown as "Average RIR about 2" or, in RPE mode, "Average RPE about 8" (10 − average, nearest 0.5).
- Hard set = done working set with RIR <= logger.hardRIR (3) or no RIR logged (logging-spec §5). A 4+ set is never a hard set, so the far-from-failure line (average >= 3) sits at the edge of the hard-set rule: the same number, read the same way.

## 8. One deload rule (reconciling logging-spec §5, §9 and this tab)
Before progress2 there were two overlapping deload ideas: logging-spec §9 ("performance drop on 2+ consecutive exposures for ≥ 2 lifts within 14 days", RIR drift, missed reps; fire on 2+ signals or 6+ weeks) as implemented in `tools/deload.py` from `rules.json logger.deload_signals` (a points model), and the Progress tab's own "several lifts dropping" signal. **There is now one rule:**
- There is one deload rule: logger.deload_signals points (tools/deload.py deload_check: eligibility, weeks since deload, RIR drift, hard sets over target, readiness, suggest_score 3), with its performance signal REPLACED by the Progress lift statuses below. Progress, Train and Log all use it: rules.json logger.deload_signals.performance = {"source": "progress-rules.json#deload", ...inline values} since progress3, and tools/deload.py deload_check calls tools/progress.py perf_signal.
- **Performance signal (replaces the old one):** several lifts dropping = >= 2 lifts with status dropping whose latest exposure is in the last 14 days → **2 points**; otherwise, >= 3 lifts with a status and >= 60% of them stalled or dropping → 1 point. "Dropping" is the §4 lift status, so the Log, Train and Progress tabs share one definition (it matches logging-spec §9's 2-consecutive-drops wording).
- **Unchanged signals** from `logger.deload_signals`: eligibility (≥ 4 logged weeks, ≥ 8 sessions, ≥ 4 weeks since the last deload), weeks since the last deload (6 → 1, 8 → 2, 10 → 3 points), RIR drift, hard sets over target, readiness. Suggest at the `suggest_score` (3).
- **Hard-set rule overlap:** the "hard sets over target" signal counts hard sets with logging-spec §5's rule (RIR ≤ `settings.hardRIR`, default 3, or no RIR). The Progress effort summary uses the same RIR values and the same stored scale (0–4); a set logged 4+ is never hard, and the far-from-failure note (average ≥ 3) is a display note, **not** a deload signal. RIR drift stays in the deload rule only.
- The deload is never applied to the board: a deload is a temporary week overlay (logging-spec §9); the board is not changed. When it is suggested it is the single needs-attention item (§6).
- **In rules.json since progress3** (approved by Chief of Staff, Oct 24, 2026; applied by `tools/build_progress.py apply_rules`, sources `tools/rules_v29_blocks.py` and `tools/build_rules_v29.py`): `logger.deload_signals.performance` = `{"source": "progress-rules.json#deload", several_lifts_dropping, mostly_stalled, ...}` and `logger.e1rm_max_reps` = 12. `tools/deload.py deload_check` sees the source and calls `tools/progress.py perf_signal`, so the Train tab's deload prompt and the Progress tab use the same code path.

## 9. Wins
- Kinds and rank: milestone 1, strongest_ever 2, e1rm_pr 3, load_pr 4, rep_pr 5, hold_pr 5, vs_3_months 6 (lower shows first). Window: last 14 days; at most 5 shown, the rest behind "+N more".
- The first session with an exercise sets its baseline: no win from it.
- **e1RM PR:** best estimated 1RM above every earlier one by more than review.flat_pct (1%) (e1rm lifts). **Strongest ever:** an estimated 1RM PR that is still the all-time best at as_of, on a lift with >= 28 days of history: shown as "Strongest ever".
- **Load PR:** heaviest logged load above every earlier one by more than half a step (e1rm, core, distance lifts; bodyweight lifts with added load). **Rep PR at a weight:** more reps in one working set than ever at that load or heavier (earlier sets within half a step count as the same load); bodyweight lifts with no added load: more reps than ever. **Hold PR:** longer hold than ever (hold lifts).
- **Plate milestones:** 135, 225, 315, 405 lb (60, 100, 140, 180 kg) for `barbell-bench-press`, `back-squat`, `deadlift`: first done working set with >= 1 rep at a logged load >= the milestone (session unit; kg sessions use plates_kg), after the baseline session.
- **vs 3 months ago:** the dashboard change (best of the first 14 days of the 91-day window vs best of the last 14 days; estimated 1RM, load-reps index, best reps at bodyweight or best hold); shown as a win only if >= +1% and the lift has no other win in the list.
- **Dedupe:** one win per lift per session (highest kind); then one win per lift in the list (best kind, newest); vs_3_months only for lifts with no other win, at most 2. **Sort:** kind rank, then lifts that are some muscle's main lift first, then exercise type (primary, accessory, isolation), then date (newest first), then gain % (desc), then exercise id.

## 10. Minimum data and honest labels
- gain vs last: 2 exposures
- lift trend: 3 exposures in >= 3 weeks spanning >= 14 days (42-day window)
- lift stall: 4 exposures spanning >= 21 days
- lift dropping: 4 exposures
- muscle trend: 1 lift with a trend and >= 3 weeks with credited sets
- muscle stall: muscle trend + main lift status
- deload: logger.deload_signals.eligible (>= 4 logged weeks, >= 8 sessions, >= 4 weeks since the last deload)
- wins: a baseline session per lift; vs 3 months needs data in both windows
- Labels: "Not enough sessions yet ({have} of {need})", "Not enough weeks yet". Never a trend, stall, rate or deload call below the minimum.
- Always visible: "Strength and performance, not measured muscle growth". All numbers say "about" or "estimated"; no claims about muscle growth, health or injury.

## 13. Dashboard (progress3)
Progress dashboard (KPI strip, body map, muscle table, win chips, dot charts). Strength and performance, not measured muscle growth. Every threshold is a modelling choice [M]. Payload: `report()['dashboard']` (`window`, `label`, `kpis`, `muscles`, `lifts`).

**Window.** 3 months = the 91 days ending at as_of (as_of - 90 .. as_of), local dates; deload sessions never count. Sparklines and the 12w dot window use the 12 Monday weeks ending with the week of as_of, which sit inside it.

**One value per session (the dashboard metric).** one dashboard value per lift session, by lift kind: e1rm lifts -> estimated 1RM (Epley, sets <= 12 reps); core / carry / high-rep lifts -> load_index; bodyweight lifts -> best_reps; hold lifts -> best hold (s); core lifts with no load -> best_reps.
- **Best reps** (bodyweight lifts): most reps in one done working set at bodyweight (added load within half a load step of 0); weighted and assisted sets are left out of Best reps (they still count for load PRs and hard sets). A session with no bodyweight set has no Best reps value.
- **Weighted / assisted variants:** a bodyweight lift logged only with added load (e.g. weighted dips) has no Best reps in the window: change and band are insufficient ("weighted sets only"); its progress shows as load PRs. No bodyweight-included 1RM is shown.
- Labels: e1rm = "estimated 1RM", load_index = "load-reps index", best_reps = "best reps", hold_s = "best hold".

**3-month change (one definition for the KPI, the table, the body map and "vs 3 months ago").**
- Early: best dashboard value in the first 14 days of the window that has this lift: from its first non-deload session in the window (s) to s + 13. Late: best dashboard value in the last 14 days (as_of - 13 .. as_of).
- Change % = (late / early - 1) x 100; weeks = (as_of - 13 - s) / 7, the gap between the two 14-day periods; rate = pct / weeks.
- Minimum data: >= 4 non-deload sessions in the window, a value in both periods, and s <= as_of - 56 (>= 8 weeks of data, so the periods are >= 30 days apart). Otherwise `change.status = "insufficient"` with a reason ("fewer than 4 sessions in 3 months", "less than 8 weeks of data", "no session in the last 2 weeks", "weighted sets only").
- Rounding: stored to 2 decimals; shown to the nearest 0.5% from 1% up, one decimal below 1% (e.g. "+12.5%", "+0.8%").

**Body map band (per muscle, from its main lift's change rate) [M].** up_strong > +1.5 %/week; up > +0.5; down < -1.0; flat = -1.0 .. +0.5 inclusive (the flat band). Up and down are the 42-day trend thresholds (logger.progress_signals), applied to the 3-month change rate.
- Colour roles (colours are the Builder's): up_strong → progress-strong, up → progress, flat → neutral, down → attention, insufficient → muted, not_trained → none.
- A muscle with the stall flag (muscle.stuck) keeps its band colour and gets the attention marker (outline / dot); the KPI counts it as stalled or dropping. Muscles with no lift crediting them (rating >= 0.25) in the window: not coloured, not counted.

**KPI strip.**
1. **Strength change vs 3 months ago** [M]: median of those lifts' change pct (even count: mean of the middle two); lifts = unique main lifts of the trained muscles (a lift that is main for several muscles counts once) whose dashboard metric is e1rm or load_index and whose change has enough data; at least 3 lifts, else "Not enough data". Rounding: nearest 0.5% from 1% up, one decimal below 1%. Sublabel: "Median of main lifts (estimated 1RM, or the load-reps index for high-rep lifts). Strength and performance, not measured muscle growth."
   - Why the median: Median over unique lifts: one new or fast-moving lift (e.g. a lift added late or recovering from a break) cannot swing it, and a lift that is main for four muscles (deadlift) is not counted four times. A mean weighted by stimulus would mostly repeat the biggest compound lifts. Best reps and hold changes are left out: their percentages run on a different scale (one more rep at 10 reps is +10%, about +3% estimated 1RM), so mixing them would inflate the median. They show in the table and in vs 3 months ago instead.
2. **Muscles progressing / flat / stalled or dropping** [M]: trained muscles only. stalled_or_dropping = muscle stall flag (muscle.stuck) OR band down (the stall flag has its own minimum data, so a stalled muscle counts here even when its 3-month band is insufficient); else progressing = band up_strong or up; else flat = band flat; else (band insufficient) not in a bucket, shown as the insufficient count.
3. **PRs, last 30 days**: wins events (same PR definitions as wins: estimated 1RM PR on sets <= 12 reps, load PR, rep PR at a weight, hold PR, plate milestone, strongest ever) dated in the last 30 days (as_of - 29 .. as_of); one per lift per session (highest kind); vs 3 months ago is not a PR. Audit: progress4 check (2026-10-24): no inflation from rep PRs at many weights. Events are already one per lift per session (highest kind), and a rep PR is reported once per session at the heaviest weight that beat the earlier best reps at that weight or heavier. On the sample all 54 rep PRs in the last 30 days are top-weight sets and also new plotted bests; the count is high because double progression gives a rep PR almost every session. Count kept unchanged.
4. **Average RIR, last 28 days** (`kpis.avg_rir`, progress4) [M]: plain mean of logged RIR over done working sets in the last 28 days (as_of - 27 .. as_of), deload sessions left out; 4+ counts as 4; sets with no RIR are skipped; each set counts once. Same pool, window and minimum as the per-muscle effort.avg_rir (which weights each set by muscle rating); rounded to 1 decimal. `share_logged` = logged_sets / eligible_sets, where eligible = every done working set in the same pool, RIR logged or not. Fewer than 6 logged sets: value null, reason "not enough RIR logged". Display "Average RIR {v}" (RPE mode "Average RPE {v}", RPE = 10 - RIR); when share_logged < 50% add the note "Based on the {n} of {total} sets with RIR logged".

**Muscle table.** Columns: muscle, sparkline_12w, main_lift, change_pct, avg_rir. Change % = the main lift's change pct (dashboard.change); same main lift as the muscle cards (pinned, else most sessions in the 42-day window). Avg RIR = effort.avg_rir (28 days, stimulus-weighted).
- **Sparkline:** the main lift's weekly best dashboard value for the 12 Monday-to-Sunday weeks ending with the week of as_of, oldest first; null for weeks with no value (a week with only deload sessions is null like any empty week; the deload_week flag was removed in progress5). Why not a combined muscle index: one lift's own number (estimated 1RM, reps or hold) is easy to read and matches the change %; a combined muscle index would need weights and units nobody can check.

**Dot charts (per lift).** A dot is one per session with the lift: the session's best set as its dashboard value (estimated 1RM, load-reps index, best reps or best hold). Windows: 4w = sessions in the last 28 days, 12w = sessions in the last 84 days, All = every logged session (`dot.days_ago` makes the filter simple). dot.pr = true when that session has a wins event for the lift (any PR kind); used for event chips and tooltips, not for the chart marker. dot.best = true only when the dot's plotted value (dot.value, as stored) is strictly higher than every earlier dot value of that lift, over all history (not only the window shown); the lift's first-ever session and deload dots are false. The chart marker uses best (`dot.best`, progress4). Deload sessions produce no dot at all (progress5, deload_sessions = exclude); the dot.deload field was removed.

**vs 3 months ago.** Wins vs 3 months ago uses this change for every lift with enough data, including bodyweight lifts (best reps) and hold lifts (best hold). Bodyweight and hold lifts join because the logs carry them every week; their % is reps or seconds, so the KPI median leaves them out (above).

## 15. Headline strip, % overlay and table rows (progress7)
progress7 headline strip (Mr Dude via Chief of Staff, Oct 25, 2026). Strength and performance only; every threshold is a modelling choice [M]. Payload: `report()['dashboard']['headline']` (`strength_score`, `prs_this_month`, `streak`, `muscle_mix`), `['overlay']`, `['table_rows']`.

**1. Strength Index** [M]. Strength Index = 100 x geometric mean over the unique main lifts (after overrides and the table dedupe) of late / early, where early and late are the dashboard change values (best of the first 14 days of the 91-day window vs best of the last 14 days); only lifts on the estimated-1RM scale (estimated 1RM or the load-reps index) with an ok change; >= 3 lifts, else "Not enough data"; shown as a whole number (half up).
- Arrow: mean of those lifts' 42-day trend pct_per_week (lift_trend), with the same thresholds: up > +0.5 %/week, down < -1.0, else flat; needs >= 2 of the lifts with a trend, else no arrow.
- Why this normalisation: Personal and unitless: each lift is compared only with itself, so a 140 lb curl and a 400 lb deadlift weigh the same; the geometric mean of ratios is the standard way to average relative changes (a +10% and a -10% lift give about 99, not a misleading 100 from 10 lifts' sums) and is not dominated by the heaviest lift as a summed total would be. Using the dashboard change values means the score, the table change % and the overlay share one baseline. Reps and hold ratios move on a different scale (7 -> 12 reps is +71%), so they stay out, as in the strength-change KPI. Bodyweight-relative scores and DOTS / Wilks need bodyweight and sex and only fit squat / bench / deadlift totals.
- Bodyweight check: the Train log carries history.bodyweights[] (the sample logs one a week) but settings carry no sex; DOTS is therefore an optional later variant only. DOTS: optional later variant: needs settings.sex and a logged bodyweight; applies to the squat + bench + deadlift estimated-1RM total only; never the default.
- Label / sublabel: "Strength Index" / "Model, not a measurement. 100 = your level at the start of the last 3 months.". It is a ratio to your own start, not a strength level and not comparable between people.
- Relation to the strength-change KPI: the KPI is the median % of the same lifts; the index is their geometric mean as a ratio. They agree in direction; the index can sit a little off the median when lifts spread (sample: KPI +15%, index 114).

**2. PRs this month** [M]. unique main lifts (after overrides and the table dedupe) whose best plotted value (dashboard dot) in the last 30 days (as_of - 29 .. as_of) beats their best plotted value from before those 30 days: by >= 1% on the estimated-1RM scale (estimated 1RM, load-reps index; the PR tie rule) or by >= 1 rep / second (Best reps, hold); one per lift, dated at the first session that reached it (that dot has best = true). A lift first logged inside the 30 days has no earlier best and does not count. Deload sessions never have dots.
- This month = rolling last 30 days, not calendar month to date: it does not drop to 0 on the 1st, reads the same on any day and matches prs_30d and wins.
- Why one per lift: one per lift per session (every dot with best = true) gives several per lift on the sample (progress-spec §15), because its double progression sets a new best almost every session; counting each main lift once a month answers "on how many main lifts did I set a record this month" and stays readable (at most the number of main lifts). new_best_sessions keeps the per-session count as detail.
- prs_30d: kept unchanged for back-compat (all PR events of every lift, feeds the wins list detail); the headline chip uses prs_this_month.

**3. Weekly streak** [M]. consecutive Monday-to-Sunday weeks in which completed non-deload sessions >= the routine's planned training days (routine days with at least one tile; no routine: 2). Skipped and unfinished sessions do not count.
- Deload weeks: a week with a deload session (session.deload === true) or inside a history.deloads overlay: with >= 1 logged session it keeps the streak but does not add to it; with 0 sessions it breaks it (a week that still meets the target with non-deload sessions counts as met). Why: a planned lighter week should not cost a streak, but an empty week is a missed week whatever it was called.
- Current week: the week of as_of never breaks the streak; it adds 1 once it is met. Best: the longest run over the whole log (same rule).

**4. Muscle mix.** trained muscles by their 91-day body-map band: up = up_strong or up, holding = flat, down = down; insufficient and not_trained are separate counts; stalled is a marker (stalled_marker list), never a fourth bucket.
- Versus the muscle counts: kpis.muscle_counts (progressing / flat / stalled or dropping) moves a stalled muscle into "stalled or dropping" whatever its band; muscle_mix only reads the band, so a stalled muscle with a flat band is "holding" here and "stalled or dropping" there. Both use the same bands and main lifts.

**5. % change overlay.** for each unique main lift (after overrides and the table dedupe): every non-deload session dot in the 91-day dashboard window as pct = (session value / baseline - 1) x 100, stored to 2 decimals.
- Baseline: baseline = the lift's dashboard change early value: the best value of the first 14 days of the window (from its first session in the window). Best-of-14-days ignores one weak first session; it is the same number the table change %, the Strength Index and vs 3 months ago use, so the best overlay point in the last 14 days equals the table change % exactly (a median of the first 3 sessions was considered and rejected because the overlay and table would then disagree).
- Missing baseline: change status insufficient (any reason, including "main lift not trained recently"): baseline null, points [], reason shown, no line drawn.
- Units: bodyweight lifts plot best reps and holds plot seconds in the same % space; unit_flag tells the chart to mark them (reps and seconds move faster in % than estimated 1RM); flags e1rm → estimated_1rm, load_index → load_index, best_reps → reps, hold_s → seconds.

**6. Main lift choice and table rows.** progress7 (Chief of Staff, Oct 25, 2026; replaces "most sessions among lifts rated >= 0.5"). Candidates = lifts crediting the muscle >= 0.25 with a non-deload session in the 42-day window. 1) an override / pin always wins; 2) specific: for every muscle first, a lift where the muscle is the main mover (ratio >= 0.75) and the lift's primary muscle (its highest ratio, ties allowed); 3) other muscles, in muscle order: lifts rated >= 0.5 (none: >= 0.25), preferring one that is not already another muscle's main lift; a shared lift only when nothing unshared qualifies. Ties everywhere: most sessions in the window, higher ratio, more credited sets, primary < accessory < isolation, id.
- Why: a compound lift that credits many muscles (deadlift) no longer becomes the main lift of four muscles when a muscle-specific lift is trained; the table stops repeating the same row and the KPI / score do not count a lift once per muscle.
- Rows: progress7: dashboard.table_rows = one row per unique main lift of the trained muscles, in muscle order of its first muscle; a lift that is the main lift of several muscles (only when nothing unshared qualifies, muscle.main_lift_choice) is one row listing those muscles, label "<lift> — <muscle>, <muscle>"; single-muscle rows are labelled with the lift name. Avg RIR: one muscle: that muscle's effort.avg_rir; shared row: plain mean of its muscles' avg_rir (nulls skipped), with avg_rir_by_muscle alongside. Dashboard.muscles stays one entry per muscle for the body map (a shared lift colours each of its muscles with the same band).
- Change versus the old rule (most sessions among lifts rated >= 0.5): muscle-specific lifts win first, and a lift already used by another muscle is taken only when nothing else qualifies. Overrides still win.

## 16. Muscle table order and % change chart default (order1)
order1 (Mr Dude via Builder, Oct 25, 2026): default order of the Progress muscle table and table_rows. Display only; never changes any number.

**Input.** report(..., prefs={bias_muscles: [...]}) - the existing ranking prefs field (tools/rank.py prefs.bias_muscles; storyboard localStorage apechit.sb.bias), in the order the user picked them. Ids = exercises.json muscles or regions ids (a region counts as its parent muscle, exercises.json regionGroup). Same cleaning as rank.py _bias: unknown ids dropped, duplicates dropped, first ranking.bias.max (3) kept; ids past the cap are listed in muscle_order_meta.ignored. Goals (prefs.goals) do not reorder the table: their muscle_priority weights are whole-goal multipliers, not a user-stated order.

**muscle_order rule.** priority muscles first, in the user's stated order (after region -> parent mapping and dedupe); then the other trained muscles, then the not-trained muscles, each in the fixed exercises.json muscles order (chest, front delts, side delts, rear delts, lats, upper back, traps, biceps, triceps, forearms, abs, quads, hamstrings, glutes, calves, adductors, lower back, obliques, abductors). A priority muscle stays first even when not trained.
- Why a fixed order: a fixed anatomical order keeps every row in the same place week to week (sorting by weekly sets would reshuffle the table after every session and make the sparkline column hard to scan); it is the same order the body map, kpis and the rest of the app already use, and it is a total order, so there are no ties to break.
- Ties: none: priority order is the user's list; the rest follow a fixed list.
- Output: dashboard.muscle_order = [{muscle, priority: bool, priority_rank: 1..3 | null, trained: bool, bias_ids: [ids that mapped to it]}] covering every muscle once; dashboard.muscle_order_meta = {priority: [muscles], ignored: [ids], cap}.
- table_rows: table_rows are sorted by the muscle_order position of their highest-placed muscle (for a shared-lift row: its highest-priority muscle); a row's muscles list (and its label) follows muscle_order too; row.priority = any of its muscles is a priority muscle. With no priorities this is exactly the progress7 order.

**chart_default rule** (cap 6). 1) main lifts of the priority muscles, in priority order (muscle_order), deduped; 2) the ladder core lifts in slot order (bench, squat, deadlift, overhead press, pull-ups), each the core exercise if logged, else its stand-in if logged, deduped; keep eligible lifts only, in that order, up to cap. "+ more" = every other eligible lift from those two groups plus the remaining overlay main lifts in table_rows order, deduped.
- Eligible: a lift is eligible when its 91-day change has status ok (it has a baseline and points, the same rule that draws an overlay line); a main lift uses its overlay row status (so "main lift not trained recently" is not eligible).
- Ladder core: [slot, exercise id, stand-in id] - mirrors data/evolution-rules.json lifts / substitution (dips stand in for bench, barbell row for pull-ups). The stand-in is used only when the core exercise has never been logged (no exposure at all), as on the ladder.
- Skipped: chart_default.skipped lists why a candidate is not drawn: no_main_lift (priority muscle with no main lift), insufficient (not eligible), over_cap is not a reason (those lifts are in more).
- Series: chart_default.extra_series = overlay-format rows (same baseline and points rule) for chart lifts that are not main lifts and so are not in overlay.lifts; together they give every line the chart can draw.
- Output: dashboard.chart_default = {lifts: [{lift, source: priority | ladder, muscles: [priority muscles it covers], slot: ladder slot | null, stand_in: bool}], more: [lift ids], skipped: [{lift | null, muscle | null, slot | null, reason}], cap, extra_series: [...]}.

## 17. Chart metric toggle (metric1)
metric1: the metric toggle on each muscle's full-size main-lift chart. Every option is a performance measure of that lift in that session (load moved, reps, time); none is a measure of muscle growth. Display only: the dashboard change %, bands, KPIs and headline keep using est_1rm.

**Options** (4; default `est_1rm`):
- `est_1rm` (Est. 1RM, estimated): exactly the current chart value: dashboard.lifts[lift].dots[].value (dash_metric): estimated 1RM (Epley, best set <= 12 reps) for barbell/machine lifts; the load-reps index for high-rep (no set <= 12 reps in the window), loaded core and carry lifts; best reps at bodyweight for bodyweight lifts; best hold (s) for holds. For the last three the option label switches to that metric's label (dashboard.metric.labels). Stored as kg (estimated 1RM, load-reps index) | reps | s.
- `heaviest` (Heaviest): the heaviest load in one eligible working set with >= 1 rep (bodyweight lifts: the effective load above). Reps of that set are kept for the tooltip; ties on load -> more reps, then the earlier set. Stored as kg.
- `best_set_volume` (Best set volume): max over eligible working sets of load x reps (bodyweight lifts: effective load x reps). Stored as kg x reps.
- `session_tonnage` (Session tonnage): sum over every working set of the lift in the session of load x reps (bodyweight lifts: effective load x reps). Depends on how many sets were planned, so it reads as work done, not strength. Stored as kg.

**Persisted choice:** `settings.progress.chartMetric`, global (one choice for every muscle chart). the choice is a reading preference ("show me tonnage"), not a property of a muscle; one key means one tap changes every chart, nothing to keep in sync per muscle, and a muscle whose main lift changes keeps the same view. Fallback: if the saved option is unavailable for the lift on screen, that chart shows metric_series[lift].fallback = est_1rm, or (when est_1rm itself has no points, e.g. a lift logged only with added load or only on an assisted machine) the first available option in options order; the disabled option shows its reason; the saved value is not overwritten. An unknown or missing saved value = est_1rm. No available option -> the chart empty state.

**Which sets count.** done working sets with reps >= 1 in completed, non-deload sessions (session.deload === true excluded), up to as_of; warm-ups never count; aliases resolved; loads converted to kg internally (prs.py flatten). Tags: a set tagged in logger.set_tags is left out of an option when the matching PR type is in that tag's pr_exclude: est_1rm <- e1rm, heaviest <- weight, best_set_volume <- set_volume. session_tonnage counts every working set, tagged or not (logger.set_tags.volume: load x reps of every tagged working set stays in logged volume). Rep cap: the 12-rep cap (rules.json logger.e1rm_max_reps) applies only to est_1rm. heaviest, best_set_volume and session_tonnage use sets of any rep count.

**Load.** lifts without exercises.json bodyweight_fraction: load = the logged load. lifts with bodyweight_fraction f (pull-ups, dips, push-ups ...): load = f x BW + added load; assisted machines (bodyweight_assisted) and negative logged loads: max(0, f x BW - assistance). BW = the bodyweight of the set's day with the evolution ladder fallback (data/evolution-rules.json bodyweight.rule): latest history.bodyweights entry on or before the session's local date, else settings.profile.bodyweight, else none. No backfill from a later entry. No bodyweight: a bodyweight-lift session with no bodyweight gets no point on the weight options (it still has its est_1rm point = best reps); the skipped sessions are counted in metric_series[lift].options[o].skipped_no_bodyweight. If no session of the lift has a bodyweight, heaviest / best_set_volume / session_tonnage are unavailable with reason no_bodyweight. weight options on bodyweight lifts include bodyweight; the axis and tooltip say so ("incl. bodyweight").

**By lift kind:**
- e1rm: all four options
- load_index: high-rep and loaded core lifts: all four options (est_1rm shows the load-reps index)
- distance: carries (reps field = metres): est_1rm (load-reps index) and heaviest; best_set_volume and session_tonnage unavailable (reason distance)
- bodyweight: all four; est_1rm = best reps; weight options need a bodyweight (load rule)
- core_unloaded: core lifts never logged with a load: est_1rm (best reps) only; weight options unavailable (reason no_load)
- hold: est_1rm (best hold, s) only; weight options unavailable (reason hold). Seconds x load was considered and left out: it mixes two units and a longer hold at the same load already shows on the hold chart.

**Availability.** an option is available when its series has >= 1 point; otherwise unavailable with the first matching reason: hold, distance, no_load (no session with load > 0 and no bodyweight factor), no_bodyweight, no_data. Reason strings: hold = "Timed hold: this chart shows hold time only"; distance = "Carry: load x distance is not charted"; no_load = "No weight logged for this lift"; no_bodyweight = "Log your bodyweight to chart weight for this lift"; no_data = "No sessions with this measure yet".

**Axis labels:** est_1rm by metric e1rm "Estimated 1RM ({unit})", load_index "Load-reps index ({unit})", best_reps "Best reps", hold_s "Best hold (s)"; heaviest "Heaviest set ({unit})", best_set_volume "Best set volume ({unit} x reps)", session_tonnage "Session tonnage ({unit})"; bodyweight lifts add ", incl. bodyweight". Units: settings.unit (lb default | kg); values are stored in kg and converted for display.
**Number format:** est_1rm: as dashboard dots (lb whole number, kg nearest 0.5; reps and seconds whole); heaviest: nearest 0.5 in the display unit (2.5 lb and 1.25 kg plates stay visible), trailing .0 dropped; best_set_volume: whole number in the display unit, half up, thousands separator ","; session_tonnage: whole number in the display unit, half up, thousands separator ",".

**PR dots.** point.pr = the session value is a strictly new all-time best for that option over this lift's non-deload history (deload sessions have no points); the first point is the baseline and never a PR; ties are not PRs.
- est_1rm: identical to dashboard dot.best (strictly above every earlier plotted value, 1e-9), so the default chart is unchanged
- heaviest: load > previous best + logger.prs.tie.step_fraction (0.5) x the smallest real load step at that load (prs.py step_kg, same as the weight PR): kg/lb rounding and bodyweight drift below half a step are ties
- best_set_volume: value > previous best x (1 + review.flat_pct / 100) (>= 1%, the set_volume / e1rm PR tie rule and the headline min_gain_pct)
- session_tonnage: value > previous best x (1 + review.flat_pct / 100) (>= 1%)
- reps_and_holds: est_1rm on best reps / best hold: strictly more (>= 1 rep or 1 s), as dot.best

**Tooltips:** est_1rm: "{date}: {display} (estimated)"; est_1rm_reps: "{date}: {display}"; heaviest: "{date}: {load} {unit} x {reps}{bw}"; best_set_volume: "{date}: {load} {unit} x {reps} = {value} {unit} x reps{bw}"; session_tonnage: "{date}: {value} {unit} over {sets} working sets{bw}"; bw: " (incl. {bw} {unit} bodyweight)"; pr_suffix: " • new best" (date as YYYY-MM-DD in the reference; the app may localise it).
**Empty state:** 0 points -> option unavailable (no_data); 1 point -> a single dot, no line; >= 2 points -> line + dots. Strings: "No sessions with this measure yet" / "One session so far: log another to see a line".
**Trend / % change:** the 3-month change %, band and trend words stay est_1rm only (dashboard.change); the other options show no % and no trend line. Why: heaviest moves in plate-sized steps and often repeats, so a % between two windows is mostly rounding; best set volume swings with the rep target of the day; tonnage scales with the number of sets planned. They are useful to look at, not to score.

**Considered and not offered:**
- best_reps_at_weight: needs a second control (which weight), and reps at a fixed load already show as rep PRs in wins; not clearly better than heaviest + best set volume
- weekly_volume: a muscle-level weekly series (sets or tonnage across lifts), not a property of the charted lift; it is noisy (one missed session halves it) and already shown as weekly hard sets elsewhere

**Output.** report().metric_series = {lift: {kind, bodyweight_lift, options: {option: {available, reason, reason_text, label, axis, unit, points: [{date, session_id, value, display, pr, ...detail}], skipped_no_bodyweight, trend}}}} for every logged lift (main lifts and the rest), plus report().chart_metrics_meta = {options, default, persist_key}.

**Sample.** Barbell bench press: est_1rm last 300 lb (7 PR dots); heaviest last 225 lb (3 PR dots); best_set_volume last 2,250 lb x reps (7 PR dots); session_tonnage last 6,075 lb (7 PR dots). Pull-up: heaviest last 201.5 lb incl. bodyweight, 0 heaviest PR dots (the weekly +0.2 lb bodyweight drift stays under half a load step). Side plank: weight options unavailable (hold).

**Edge cases** (`progress-reference.json` edge_cases `metric_*`):
- `metric_bodyweight_weighted_assisted`: pull-up with strict, weighted (+25 / +45 lb) and assisted (-30 lb) sets, plus the assisted pull-up machine: weight options use 0.95 x bodyweight + added (assisted: minus the assistance); est_1rm stays best reps at bodyweight.
- `metric_timed_hold`: timed holds: est_1rm = best hold (s); heaviest / best set volume / session tonnage unavailable (reason hold).
- `metric_load_index`: load-index lifts: high-rep leg press (no set <= 12 reps) and loaded cable crunch get all four options (est_1rm = load-reps index); the farmer carry gets est_1rm and heaviest (volume and tonnage: reason distance); the unloaded ab-wheel rollout gets est_1rm (best reps) only (reason no_load).
- `metric_deload_week`: the week-4 deload session (session.deload === true) logs 3 x 405 lb: no point and no PR on any option.
- `metric_missing_bodyweight`: no bodyweight entries and no profile bodyweight: weight options on pull-ups and weighted dips are unavailable (reason no_bodyweight); pull-up est_1rm (best reps) still draws; weighted dip has no est_1rm point (weighted sets only).
- `metric_bodyweight_partial`: first weigh-in on Aug 17: the two earlier sessions of each lift get no weight point (skipped_no_bodyweight = 2; no backfill from a later entry, the evolution ladder rule).
- `metric_kg_units`: kg log and unit setting: axes in kg, heaviest to the nearest 0.5 kg, volume and tonnage whole kg.
- `metric_pr_ties`: bench (5 lb step): a repeat of 225 x 5 ties everything; 227.5 (+ half a step) ties heaviest but is a >= 1% volume and tonnage PR; 232.5 is a heaviest PR; week 5 (232.5, 232.5, 237.5) is a heaviest and volume PR but only +0.7% tonnage (tie); week 6 3 x 237.5 is a +1.4% tonnage PR and a heaviest / volume tie. Squat: a 315 x 3 set tagged partials is left out of heaviest and best set volume but counts in session tonnage.
